# Task registry and mailbox

Open the prototype with `start-center.ps1`, then select **Tasks** in the dashboard.
The task registry and messages live in `team-center.json` inside the active
`DOTPALS_HOME` profile (`.dotpals-center/` for the prototype). Activity expiration
and clearing activity history do not remove tasks or messages. Back up this profile
to preserve machine-local work. This is not a multi-machine sync service.

## Working from the team folder

Start the coordinating CLI from the team context folder. Create a task with the
goal, scope, acceptance criteria, context folder, code checkout/worktree, branch
and contract version. Choose its coordinator's exact native session identity.

Each task has one Raphael coordinator, represented by a participant ID. The
provider is independent of the role: Codex, Claude, Gemini or Antigravity can be
the coordinator. Add workers with their native session IDs, roles, working folders
and allowed write paths. A session cannot join the same task twice. Coordinator
transfer and automated ownership leases are future work.

Three identities remain separate:

- Task ID: generated by Dotpals.
- Team session ID: optional, supplied from the team's session-registration workflow.
  Dotpals does not invent or replace a team session ID.
- Native session ID: `codex:UUID`, `claude:UUID`, `gemini:UUID` or
  `antigravity:UUID`. A bare Claude UUID is normalized to `claude:UUID`.

Known sessions come from observed native logs, saved handoffs, and task registrations.
Manually registering an ID is a declaration, not proof that its native conversation
exists. The mailbox supports all four providers without reading their native logs.

## Messages

Message types: assignment, question, answer, result, blocker, note. Select the
sender and recipient within the task; `user` represents the human. Assignments
must be from the user or coordinator. Workers can send questions and results back
to Raphael. An answer must reference a question and reverse its sender/recipient.

**Saved** means the message is in the durable mailbox. The mailbox composer alone
does not launch a CLI. The separate **สั่งราฟาเอล / ส่งคำสั่ง** form now launches
providers through the bridge; see [app-dispatch.md](app-dispatch.md). Fetching an inbox does not acknowledge
messages. A recipient explicitly marks its message as read; the dashboard also
allows the human to acknowledge on that recipient's behalf. This local profile uses
declared identities, not authenticated agent accounts. Roles and write paths are
task metadata, not a filesystem permission or process lock.

Messages retain their complete body (up to 64,000 characters), independently of
the older handoff ledger's clipped `lastResponse`. Message bodies are immutable;
send a follow-up to correct one. Each send requires `idempotencyKey`. Retry the
same intent with the same key and identical payload: it returns the original
message. Reusing a key with different content returns 409. The dashboard retains
the key after an uncertain response.

Edits and participant/link registration require the current `expectedRevision`.
A stale edit returns 409 instead of overwriting newer task data. Incoming messages
refresh the thread without replacing unsaved form drafts. Use **โหลดงานใหม่** to
reload editing forms when a revision conflict occurs; that action replaces drafts.
Blocked/paused tasks require a checkpoint describing the reason and next action.

Saved handoff links can be attached to a task if their source or destination is a
participant. Attaching a link does not launch or resume an agent and does not
automatically register a pending destination.

## Provider-neutral CLI

Any agent with authorized local shell access can use the same CLI. The bridge must
be running. Default port 5176; override with `--port` or `DOTPALS_PORT`.

```powershell
node bin/team-center.js tasks
node bin/team-center.js sessions
node bin/team-center.js show --task <task-uuid>
node bin/team-center.js inbox --session claude:<native-uuid>
node bin/team-center.js inbox --user
```

Use an absolute script path when the CLI starts from the team folder rather than
the Dotpals code checkout. Write operations accept a JSON file (`--file`) or stdin
(`--stdin`); avoid constructing nested shell commands with conversation text.

### Create

`node bin/team-center.js create --file task.json`

```json
{
  "title": "Review session handoff",
  "goal": "Describe the existing handoff flow and open questions",
  "scope": "Read-only analysis",
  "acceptance": "Report findings and relevant file paths",
  "contextDir": "<team-context-folder>",
  "codeDir": "<code-checkout>",
  "branch": "<branch>",
  "contractVersion": "v1",
  "coordinator": {
    "session": "codex:<native-uuid>",
    "teamSessionId": "<existing-team-session-id>",
    "cwd": "<team-context-folder>"
  }
}
```

### Join and update

`join --task <id> --file participant.json`:

```json
{
  "expectedRevision": 1,
  "participant": {
    "session": "claude:<native-uuid>",
    "role": "petros",
    "cwd": "<worker-context-folder>",
    "teamSessionId": "<existing-team-session-id>",
    "model": "claude-sonnet-5-5",
    "writePaths": []
  }
}
```

`update --task <id> --file update.json` takes `expectedRevision` and the fields to
change: title, goal, scope, acceptance, contextDir, codeDir, branch,
contractVersion, status or checkpoint. Fetch the task again to obtain its revision.

`bind --task <id> --file link.json` takes `expectedRevision` and `linkId` from the
existing handoff registry. It does not copy the historical transcript into messages.

### Send, reply and acknowledge

`send --task <id> --file message.json`:

```json
{
  "from": "<sender-participant-id>",
  "to": "<recipient-participant-id>",
  "type": "question",
  "body": "Which checkout should I inspect?",
  "idempotencyKey": "<unique-key-for-this-intent>"
}
```

An answer swaps `from` and `to`, sets `type` to `answer`, and includes
`replyTo: "<question-message-id>"` and a fresh idempotency key.

`read --task <id> --message <message-id> --file receipt.json` takes
`{"recipientId":"<recipient-participant-id>"}`. Add `--all` to inbox to include
acknowledged messages. Fetching messages alone never marks them read.

## HTTP contract

| Method | Endpoint | Result |
| --- | --- | --- |
| GET | `/api/team/tasks?session=provider:UUID&status=development` | Tasks, optional filters |
| POST | `/api/team/tasks` | Create task, HTTP 201 |
| GET | `/api/team/tasks/<id>` | Task and ordered messages |
| POST | `/api/team/tasks/<id>/update` | Optimistic task edit |
| POST | `/api/team/tasks/<id>/participants` | Register worker |
| POST | `/api/team/tasks/<id>/links` | Attach saved handoff |
| POST | `/api/team/tasks/<id>/messages` | Save message / return retry result |
| POST | `/api/team/tasks/<id>/messages/<message-id>/read` | Recipient acknowledgement |
| GET | `/api/team/inbox?session=provider:UUID&unread=1` | Unread recipient messages |
| GET | `/api/team/inbox?recipient=user&unread=0` | Human inbox including read messages |
| GET | `/api/team/sessions` | Known identities and supported roles/types/statuses |

POST requests require `x-dotpals: 1`. Requests with a foreign browser Origin are
rejected; the server binds to loopback. Payloads are limited to 1 MB. Validation
errors return 400, missing records 404, revision/idempotency/lock conflicts 409.
SSE events `team-task` and `team-message` notify open dashboards to refresh.
These notifications do not push a message into a native model conversation.

Disk writes use an exclusive local lock, read the current document under that
lock, fsync a temporary file, and rename it over the registry. Unreadable existing
data fails rather than resetting. A lock left after a process crash is intentionally
not auto-deleted: inspect its PID and ensure the writer stopped before recovery.
The prototype caps storage at 1,000 tasks and 20,000 messages; it rejects new entries
at the cap and never silently expires messages. Automated archival is future work.

## Scope of this increment

Implemented: registry, role/session mapping, immutable message bodies, inbox,
explicit read receipts, revisions, retry keys, handoff association, dashboard and CLI.

The subsequent [app dispatch increment](app-dispatch.md) adds a common brief,
task-bound MCP adapter, agent launch queue and actual CLI response capture.
Future increments: autonomous same-session question/answer delivery, coordinator
transfer and quota failover. No live agent request is necessary to use the mailbox.

## Human acceptance checklist

| ID | Action | Expected |
| --- | --- | --- |
| T1 | Open Tasks, create a task using a real coordinator session | Task appears with its own ID and Raphael identity |
| T2 | Add another real native session as Petros | Both identities appear; re-adding the same session is rejected |
| T3 | Send a question from Petros to Raphael, then Reply | Reply targets Petros from Raphael and references the question |
| T4 | Acknowledge the question on behalf of Raphael | Read timestamp appears; other unread messages remain unread |
| T5 | Save scope/status/checkpoint, close and reopen the prototype | Task and message history remain |
| T6 | Use a stale revision / retry a message with the same key | Stale edit rejected; identical retry returns the original message |

These are acceptance instructions, not a claim that UI or runtime tests have run.
